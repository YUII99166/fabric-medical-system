# 第三章 系统需求分析

## 3.1 业务需求分析

### 3.1.1 业务背景

传统医疗信息系统存在以下问题：
1. 各医院信息系统独立，患者跨院就诊时病历无法共享
2. 医疗数据存储在中心化服务器，存在数据泄露和篡改风险
3. 患者对自己的医疗数据缺乏控制权
4. 跨机构数据共享缺乏信任机制

### 3.1.2 业务目标

本系统旨在构建基于区块链的医疗信息共享平台，实现：
1. 多医疗机构间的安全数据共享
2. 医疗数据的防篡改和可追溯
3. 患者对医疗数据的自主控制
4. 跨院诊疗的授权访问机制

## 3.2 用户角色分析

### 3.2.1 角色定义

系统支持五种用户角色：

| 角色 | 职责 | 权限 |
|------|------|------|
| 管理员 | 系统管理、用户管理、数据监管 | 所有功能权限 |
| 医生 | 病历管理、诊疗记录、跨院查询 | 创建病历、查询授权病历 |
| 病人 | 查看病历、授权管理、订单管理 | 查看个人病历、授权访问 |
| 药店 | 药品订单管理 | 处理药品订单 |
| 保险机构 | 保险报销审核 | 审核报销申请 |

### 3.2.2 用户用例

**医生用例**：
- 创建电子病历
- 查询患者病历（需授权）
- 添加补充诊疗记录
- 跨院病历查询申请

**病人用例**：
- 查看个人病历
- 授权医生访问病历
- 管理授权请求
- 申请保险报销
- 查看药品订单

**管理员用例**：
- 用户管理（增删改查）
- 数据统计分析
- 系统监控
- 联盟链架构管理

## 3.3 需求分析

### 3.3.1 信息系统目标

一、系统总目标

本系统的目标是为社区医疗机构和患者提供一个基于区块链技术的医疗档案管理平台，帮助医疗机构实现患者病历的安全存储和跨机构共享，提供个性化的医疗服务建议，并通过区块链技术和智能合约功能，提升医疗数据的可信度和安全性，保障患者对医疗数据的自主控制能力。

二、系统功能目标

系统主要功能为，用户通过Web浏览器端输入账号密码进行登录，然后录入患者信息，医生用户可以为患者创建电子病历，通过区块链技术将病历数据存储在分布式账本中，确保数据的不可篡改性。患者用户可以查看个人病历和健康档案，并可以授权其他医院的医生访问自己的病历信息。医生可以申请跨院授权查看来自其他医院患者的病历记录，并可以添加补充诊疗记录。此外，医生还可以为患者创建药品订单，患者可以查看和管理自己的订单信息。管理员用户能够查看系统架构概览、数据统计信息，并进行用户管理操作。

三、系统性能目标

系统应具备出色的高并发承载性能，可支撑大规模用户群体同时在线使用，即便在业务高峰时段仍能维持顺畅的运行状态。在交互响应效率方面，需将用户操作（如新增患者信息、病历查询操作、查看授权申请等）的反馈时延严格控制在2秒以内，确保用户获得即时化的操作体验。区块链交易确认时间应控制在5秒以内，保证数据上链的及时性。

四、系统安全目标

安全目标包括确保用户数据的保密性、完整性和可用性。系统通过采用密码加密存储，确保用户账户的安全性，防止不法分子的入侵和账户资料滥用。对于系统中的敏感数据，如个人信息、病历数据，采用加密技术进行加密处理，确保数据在传输和存储过程中的安全性。还有就是系统会按角色设定不同的访问权限，确保每个角色只能查看和操作自己权限内的内容，杜绝越权访问和滥用风险。区块链技术的应用确保了医疗数据的不可篡改性和可追溯性，这些措施共同保障数据的安全可靠。

### 3.3.2 信息系统需求结构

通过上网查询文献和问卷调查，分析后得出用户的潜在需求。用户需要添加患者信息并对患者信息进行管理，可以看到自己有多少个患者。患者需要通过登录注册进行身份辨识，查看个人病历和健康档案，管理和审批来自医生的授权申请，以及查看药品订单信息。医生需要可以点击患者详情查看具体的病历信息、创建新病历、搜索患者病历和申请跨院授权，还可以添加补充诊疗记录和创建药品订单。药店需要查看和处理药品订单，管理订单状态信息。管理员需要进行系统管理，查看架构概览和数据统计，对用户信息进行增删改查操作，查看所有病历记录，以及管理授权请求。

基于社区医疗档案管理的用户主要需求为病历管理、跨院授权、药品订单管理和系统管理方面，针对这些需求，需要开发一个集这些功能于一体的综合系统，为患者、医生、药店和管理员提供一个针对医疗档案的平台，以助力医疗信息化建设。系统需求结构图如图3.1所示：

### 3.3.2 用户管理模块

**FR-1 用户注册**
- 支持多角色注册（医生、病人、药店）
- 医生注册需填写组织、科室、职称
- 病人注册需填写年龄、性别
- 密码加密存储

**FR-2 用户登录**
- 用户名密码登录
- 基于角色的权限控制
- 登录状态管理（Token）

**FR-3 用户管理（管理员）**
- 查看用户列表
- 创建用户
- 编辑用户信息
- 删除用户
- 批量操作

### 3.3.3 病历管理模块

**FR-4 创建病历**
- 医生创建电子病历
- 包含：主诉、现病史、体格检查、诊断、用药、医嘱
- 自动记录医生信息、医院信息
- 生成唯一病历编号
- 存储到区块链

**FR-5 查询病历**
- 病人查看个人病历
- 医生查看本院病历
- 支持按患者姓名/ID搜索
- 显示完整病历历史

**FR-6 补充诊疗记录**
- 医生添加补充记录（复诊、随访、急诊）
- 关联原始病历
- 形成完整医疗历史链
- 补充记录不可修改

### 3.3.4 跨院授权模块

**FR-7 授权申请**
- 医生申请访问其他医院患者病历
- 填写申请理由
- 系统记录申请时间和医生信息

**FR-8 授权审批**
- 患者查看授权请求列表
- 同意或拒绝授权
- 填写拒绝理由（可选）
- 授权记录上链

**FR-9 授权查询**
- 医生查看授权病历
- 患者查看授权历史
- 支持撤销授权

### 3.3.5 药品订单模块

**FR-10 创建订单**
- 基于处方创建药品订单
- 选择药店
- 自动关联处方信息

**FR-11 订单管理**
- 药店查看订单列表
- 处理订单状态
- 患者查看订单历史

### 3.3.6 保险报销模块

**FR-12 报销申请**
- 患者提交报销申请
- 关联处方信息
- 状态：处理中

**FR-13 报销审核**
- 保险机构查看申请列表
- 审核通过/拒绝
- 更新报销状态

### 3.3.7 数据统计模块

**FR-14 统计分析**
- 用户统计（按角色、组织）
- 病历统计（按医院、科室）
- 数据可视化（图表展示）
- 联盟链架构可视化

### 3.3.8 健康档案模块

**FR-15 健康档案**
- 患者查看个人健康档案
- 显示基本信息、病历历史
- 统计就诊次数、用药记录
- 数据可视化展示

## 3.4 非功能需求

### 3.4.1 性能需求

**NFR-1 响应时间**
- 页面加载时间 < 2秒
- API 响应时间 < 500ms
- 区块链交易确认 < 5秒

**NFR-2 并发性能**
- 支持 100+ 并发用户
- 数据库连接池管理
- 缓存机制优化

### 3.4.2 安全需求

**NFR-3 数据安全**
- 密码加密存储（bcrypt）
- HTTPS 加密传输
- SQL 注入防护
- XSS 攻击防护

**NFR-4 访问控制**
- 基于角色的权限控制（RBAC）
- 路由级别权限验证
- API 接口权限验证
- 区块链身份认证（MSP）

**NFR-5 数据隐私**
- 患者数据加密存储
- 细粒度访问控制
- 授权机制保护隐私
- 审计日志记录

### 3.4.3 可用性需求

**NFR-6 易用性**
- 直观的用户界面
- 响应式设计（支持多设备）
- 操作提示和帮助文档
- 错误提示友好

**NFR-7 可维护性**
- 模块化设计
- 代码注释完整
- 日志记录详细
- 配置文件管理

### 3.4.4 可扩展性需求

**NFR-8 系统扩展**
- 支持新增医疗机构节点
- 支持新增用户角色
- 支持新增业务功能
- 微服务架构预留

### 3.4.5 兼容性需求

**NFR-9 浏览器兼容**
- Chrome 90+
- Firefox 88+
- Edge 90+
- Safari 14+

**NFR-10 平台兼容**
- Windows 10+
- Linux (Ubuntu 20.04+)
- macOS 11+

## 3.5 系统约束

### 3.5.1 技术约束

1. 后端必须使用 Go 语言开发
2. 区块链平台使用 Hyperledger Fabric 1.4.12
3. 前端使用 Vue.js 2.x 框架
4. 数据库使用 MySQL 5.7+

### 3.5.2 业务约束

1. 病历数据必须存储在区块链
2. 跨院访问必须经患者授权
3. 医生必须有执业资格
4. 数据保留期限符合法规要求

### 3.5.3 环境约束

1. 服务器：Linux 操作系统
2. 内存：至少 8GB
3. 存储：至少 100GB
4. 网络：稳定的互联网连接

## 本章小结

本章详细分析了系统的业务需求、用户角色、功能需求和非功能需求。明确了五种用户角色的职责和权限，定义了用户管理、病历管理、跨院授权、药品订单、保险报销、数据统计和健康档案七大功能模块，并提出了性能、安全、可用性、可扩展性和兼容性等非功能需求。这些需求分析为后续的系统设计和实现提供了明确的指导。
