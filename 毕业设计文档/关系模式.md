# 4.3.3 关系模式

根据全局E-R图转换得到的关系模式如下：

## 1. User（用户表）

**关系模式：**
```
User(用户ID, 姓名, 密码, 角色, 性别, 年龄, 组织)
```

**约束说明：**
- 主键：用户ID
- 说明：存储系统中所有用户的基本信息，包括医生、患者、药店和管理员

**属性说明：**
- 用户ID：用户的唯一标识符
- 姓名：用户的真实姓名
- 密码：用户登录密码（加密存储）
- 角色：用户角色类型（医生/患者/药店/管理员）
- 性别：用户性别
- 年龄：用户年龄
- 组织：用户所属组织（医院、药店等）

---

## 2. Prescription（病历表）

**关系模式：**
```
Prescription(病历ID, 病历编号, 患者姓名, 主诉, 现病史, 体格检查, 诊断, 医嘱, 创建时间, 医生ID, 组织ID)
```

**约束说明：**
- 主键：病历ID
- 外键：医生ID → User(用户ID)
- 唯一键：病历编号
- 说明：存储患者的病历信息，由医生创建和维护

**属性说明：**
- 病历ID：病历的唯一标识符
- 病历编号：病历的业务编号（唯一）
- 患者姓名：患者的姓名
- 主诉：患者的主要症状描述
- 现病史：患者当前疾病的发展历史
- 体格检查：医生对患者的体格检查结果
- 诊断：医生的诊断结论
- 医嘱：医生的治疗建议和用药指导
- 创建时间：病历创建的时间戳
- 医生ID：创建该病历的医生标识（外键）
- 组织ID：创建病历的医疗机构标识

---

## 3. Supplement_Record（补充记录表）

**关系模式：**
```
Supplement_Record(补充ID, 病历ID, 现病史, 体格检查, 诊断, 医嘱, 创建时间)
```

**约束说明：**
- 主键：补充ID
- 外键：病历ID → Prescription(病历ID)
- 说明：存储对病历的补充记录，用于记录病情变化和后续诊疗信息

**属性说明：**
- 补充ID：补充记录的唯一标识符
- 病历ID：关联的病历标识（外键）
- 现病史：补充的病史信息
- 体格检查：补充的体格检查结果
- 诊断：补充的诊断信息
- 医嘱：补充的医嘱内容
- 创建时间：补充记录创建的时间戳

---

## 4. Access_Request（授权请求表）

**关系模式：**
```
Access_Request(记录ID, 病历ID, 内容, 时间)
```

**约束说明：**
- 主键：记录ID
- 外键：病历ID → Prescription(病历ID)
- 说明：存储跨组织访问病历的授权请求记录

**属性说明：**
- 记录ID：授权请求的唯一标识符
- 病历ID：请求访问的病历标识（外键）
- 内容：授权请求的具体内容和说明
- 时间：授权请求创建的时间戳

---

## 5. Drug_Order（药品订单表）

**关系模式：**
```
Drug_Order(订单ID, 药品名, 数量, 用户ID)
```

**约束说明：**
- 主键：订单ID
- 外键：用户ID → User(用户ID)
- 说明：存储药品订单信息，记录用户的药品购买记录

**属性说明：**
- 订单ID：订单的唯一标识符
- 药品名：订购的药品名称
- 数量：订购的药品数量
- 用户ID：下单用户的标识（外键）

---

## 6. Authorized_Orgs（授权组织表）

**关系模式：**
```
Authorized_Orgs(授权ID, 病历ID, 组织ID)
```

**约束说明：**
- 主键：授权ID
- 外键：病历ID → Prescription(病历ID)
- 说明：存储病历的授权组织列表,记录哪些组织被授权查看该病历

**属性说明：**
- 授权ID：授权记录的唯一标识符
- 病历ID：关联的病历标识(外键)
- 组织ID：被授权组织的MSPID标识

---

## 7. Operation_Logs（审计日志表）

**关系模式：**
```
Operation_Logs(日志ID, 用户ID, 用户名, 操作类型, 资源类型, 资源ID, 请求方法, 请求路径, IP地址, 操作状态, 错误信息, 执行时长, 操作时间)
```

**约束说明：**
- 主键：日志ID
- 外键：用户ID → User(用户ID)
- 说明：记录系统所有操作日志,用于审计追踪和安全分析

**属性说明：**
- 日志ID：日志记录的唯一标识符
- 用户ID：操作用户的标识(外键)
- 用户名：操作用户的用户名
- 操作类型：操作的类型(如user.login、prescription.create等)
- 资源类型：操作的资源类型(如prescription、user等)
- 资源ID：操作的资源标识
- 请求方法：HTTP请求方法(GET/POST/PUT/DELETE)
- 请求路径：请求的URL路径
- IP地址：操作来源的IP地址
- 操作状态：操作执行状态(success/failed)
- 错误信息：操作失败时的错误信息
- 执行时长：操作执行耗时(毫秒)
- 操作时间：操作发生的时间戳

---

## 关系说明

### 实体间联系

1. **用户-创建-病历（1:n）**
   - 一个用户（医生）可以创建多个病历
   - 每个病历由一个医生创建
   - 通过Prescription表中的医生ID外键实现

2. **病历-补充-补充记录（1:n，标识关系）**
   - 一个病历可以有多个补充记录
   - 每个补充记录属于一个病历
   - 补充记录是弱实体，依赖于病历存在
   - 通过Supplement_Record表中的病历ID外键实现

3. **用户-添加-补充记录（1:n）**
   - 一个用户（医生）可以添加多个补充记录
   - 每个补充记录由一个医生添加

4. **病历-关联-授权请求（1:n）**
   - 一个病历可以有多个授权请求
   - 每个授权请求关联一个病历
   - 通过Access_Request表中的病历ID外键实现

5. **用户-申请-授权请求（1:n）**
   - 一个用户可以发起多个授权请求
   - 每个授权请求由一个用户发起

6. **病历-生成-药品订单（1:n）**
   - 一个病历可以生成多个药品订单
   - 每个药品订单关联一个病历

7. **用户-处理-药品订单（m:n）**
   - 一个用户可以处理多个药品订单
   - 一个药品订单可以被多个用户处理
   - 通过Drug_Order表中的用户ID外键实现

8. **病历-授权-授权组织（1:n）**
   - 一个病历可以授权给多个组织
   - 每个授权记录关联一个病历和一个组织
   - 通过Authorized_Orgs表实现多值属性的存储

9. **用户-产生-操作日志（1:n）**
   - 一个用户可以产生多个操作日志
   - 每个操作日志记录一个用户的操作
   - 通过Operation_Logs表中的用户ID外键实现

---

## 数据完整性约束

### 实体完整性
- 每个关系模式的主键不能为空且唯一

### 参照完整性
- Prescription表的医生ID必须存在于User表中
- Supplement_Record表的病历ID必须存在于Prescription表中
- Access_Request表的病历ID必须存在于Prescription表中
- Drug_Order表的用户ID必须存在于User表中
- Authorized_Orgs表的病历ID必须存在于Prescription表中
- Operation_Logs表的用户ID必须存在于User表中

### 用户定义完整性
- 病历编号在Prescription表中必须唯一
- 角色字段只能取值：医生、患者、药店、管理员
- 创建时间、时间等时间戳字段不能为空
- 数量字段必须大于0
- 操作状态字段只能取值：success、failed
- 执行时长必须大于等于0

---

## 关系模式规范化说明

以上关系模式均满足第三范式（3NF）要求：
1. 每个关系模式都有主键，满足第一范式（1NF）
2. 所有非主属性完全依赖于主键，满足第二范式（2NF）
3. 不存在非主属性对主键的传递依赖，满足第三范式（3NF）

通过合理的关系模式设计，确保了数据的一致性、完整性和最小冗余，为系统的高效运行提供了坚实的数据基础。
