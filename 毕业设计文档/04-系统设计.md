# 第四章 系统设计

## 4.1 系统总体架构

### 4.1.1 架构设计原则

1. **分层架构**：表示层、业务层、数据层分离
2. **前后端分离**：前端独立部署，通过 API 交互
3. **模块化设计**：功能模块独立，低耦合高内聚
4. **双存储机制**：区块链+数据库，兼顾安全和性能

### 4.2.3 背书策略

```
OutOf(3, 'TaobaoMSP.member', 'JDMSP.member', 'WenjinMSP.member', 'RegCenterMSP.member')
```

系统采用多数背书策略，要求4个组织中至少3个组织成员对交易进行背书验证。这种策略设计基于以下考虑：

**安全性保障**：通过要求大多数组织参与背书，有效防止单点故障和恶意行为。即使某个组织出现问题或被恶意控制，也无法单独完成交易，确保了系统的整体安全性。

**共识机制**：遵循分布式系统中的多数原则，确保交易决策的合理性和公正性。只有当大多数参与方达成一致时，交易才能被确认和执行。

**容错能力**：允许最多1个组织离线或出现故障，系统仍能正常运行。这种设计提高了系统的可用性和鲁棒性，适应实际部署环境中可能出现的各种异常情况。

**医疗数据特殊性**：考虑到医疗信息的敏感性和重要性，多数背书策略能够提供更高的数据完整性和可信度保证，符合医疗行业对数据安全的严格要求。

## 4.3 数据库设计

### 4.3.1 概念结构设计

#### 4.3.1.1 实体识别

系统包含以下5个核心实体：

1. **用户（User）** - 强实体
   - **描述**：系统中的所有参与者，包括医生、患者、药店、管理员
   - **关键属性**：用户ID、用户名、角色、组织MSPID
   - **特殊属性**：医生职称、科室（仅医生角色）

2. **病历（Prescription）** - 强实体
   - **描述**：医生为患者开具的完整电子病历记录
   - **关键属性**：病历ID、病历编号、患者ID、医生ID
   - **核心内容**：主诉、现病史、体格检查、诊断结果、医嘱

3. **补充记录（SupplementRecord）** - 弱实体
   - **描述**：依赖于病历的后续诊疗记录和补充信息
   - **依赖关系**：完全依赖于病历实体存在
   - **关键属性**：补充记录ID、病历ID（外键）、记录类型

4. **授权请求（AccessRequest）** - 强实体
   - **描述**：医生申请查看其他医院患者病历的授权申请
   - **关键属性**：请求ID、病历ID、申请医生ID、患者ID
   - **状态管理**：待审核、已批准、已拒绝

5. **药品订单（DrugOrder）** - 强实体
   - **描述**：患者基于病历处方购买药品的订单记录
   - **关键属性**：订单ID、订单编号、患者ID、药店ID
   - **业务属性**：药品名称、数量、价格、订单状态

#### 4.3.1.2 实体联系

**核心业务关系**：

1. **用户-病历关系**：
   - **医生"开具"病历**（1:n）
     - 一个医生可以开具多个病历
     - 每个病历只能由一个医生开具
   - **患者"拥有"病历**（1:n）
     - 一个患者可以拥有多个病历
     - 每个病历只属于一个患者

2. **病历-补充记录关系**：
   - **病历"包含"补充记录**（1:n，标识性依赖）
     - 一个病历可以有多个补充记录
     - 补充记录必须依赖于病历存在（弱实体关系）
     - 病历删除时，相关补充记录自动删除

3. **跨组织授权关系**：
   - **患者"授权"医生访问**（1:n）
     - 一个患者可以授权多个医生访问其病历
   - **医生"申请"病历访问权限**（1:n）
     - 一个医生可以申请访问多个患者的病历
   - **病历"被申请"访问**（1:n）
     - 一个病历可以被多个医生申请访问

4. **药品交易关系**：
   - **患者"购买"药品**（1:n）
     - 一个患者可以有多个药品订单
   - **病历"关联"药品订单**（1:n）
     - 一个病历可以产生多个药品订单（分次购买）
   - **药店"处理"订单**（1:n）
     - 一个药店可以处理多个订单

**关系属性**：
- **授权关系**：申请理由、审批状态、申请时间、响应时间
- **购买关系**：订单状态、创建时间、总金额

#### 4.3.1.3 全局E-R图设计

**布局原则**：
1. **核心实体居中**：用户和病历作为系统核心实体，放置在图的中心位置
2. **依赖关系就近**：弱实体（补充记录）紧邻其依赖的强实体（病历）
3. **业务流程体现**：按照业务流程的逻辑顺序排列实体
4. **减少连线交叉**：通过合理的实体位置安排，最小化关系连线的交叉

**推荐布局结构**：
```
                    [授权请求]
                        |
    [用户] -------- [病历] -------- [补充记录]
     |               |
     |               |
  [药品订单] --------+
```

**图例说明**：
- **矩形**：强实体
- **双线矩形**：弱实体（补充记录）
- **菱形**：联系
- **椭圆**：属性
- **双线椭圆**：多值属性
- **虚线椭圆**：派生属性
- **下划线**：主键属性

**实体颜色编码建议**：
- **用户实体**：蓝色系（体现人员角色）
- **病历实体**：绿色系（体现医疗核心）
- **补充记录**：浅绿色系（体现医疗相关）
- **授权请求**：橙色系（体现管理流程）
- **药品订单**：紫色系（体现商业交易）

全局E-R图展示了系统中所有实体及其联系关系，体现了医疗信息管理系统的完整数据结构和业务逻辑。

### 4.3.2 逻辑结构设计（关系模式）

将E-R图转换为关系模式，得到以下7个关系：

#### 1. User（用户表）

**实体描述**：系统中所有用户的基本信息，包括医生、患者、药店、管理员等不同角色。

**属性分组**：

**基本标识属性**：
- user_id（用户ID）- 主键，系统唯一标识
- username（用户名）- 唯一键，登录标识
- account_name（账号名）- 显示名称

**认证属性**：
- password（密码）- 加密存储的登录密码

**角色属性**：
- role（角色）- 枚举值：医生、病人、药店、管理员
- organization（组织MSPID）- 所属区块链组织标识
- organization_name（组织名称）- 组织中文名称

**医生专用属性**：
- department（科室）- 医生所在科室
- doctor_title（医生职称）- 主治医师、副主任医师等

**个人信息属性**：
- age（年龄）- 用户年龄
- gender（性别）- 性别信息

**系统属性**：
- created_at（创建时间）- 账户创建时间
- updated_at（更新时间）- 最后更新时间

**关系模式**：
```sql
User(
  user_id,           -- 用户ID（主键）
  username,          -- 用户名（唯一键）
  password,          -- 密码
  account_name,      -- 账号名
  role,              -- 角色（医生/病人/药店/管理员）
  organization,      -- 组织MSPID
  organization_name, -- 组织名称
  department,        -- 科室（医生专用）
  doctor_title,      -- 医生职称（医生专用）
  age,               -- 年龄
  gender,            -- 性别
  created_at,        -- 创建时间
  updated_at         -- 更新时间
)
```

**约束条件**：
- PRIMARY KEY (user_id)
- UNIQUE KEY (username)
- CHECK (role IN ('医生', '病人', '药店', '管理员'))
- CHECK (organization IN ('TaobaoMSP', 'JDMSP', 'WenjinMSP', 'RegCenterMSP'))

### 4.3.3 数据存储策略

**双存储机制**：

1. **区块链存储**（不可篡改，所有业务数据）
   - 病历数据
   - 授权记录
   - 补充诊疗记录
   - 药品订单
   - 完整医疗历史

2. **MySQL 存储**（仅用户认证）
   - 用户认证信息（username、password、role）
   - 用于快速登录验证

**说明**：系统采用区块链为主、MySQL为辅的存储策略。所有核心业务数据（病历、授权、订单等）均存储在区块链上，确保数据的不可篡改性和可追溯性。MySQL仅用于存储用户认证信息，提供快速的登录验证服务。
