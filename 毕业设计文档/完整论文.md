# 基于区块链的医疗信息管理系统

## 摘要

随着信息技术的快速发展和"健康中国2030"战略的深入实施，医疗信息化已成为现代医疗体系建设的核心内容。然而，传统的医疗信息系统在实际应用中面临着诸多挑战：

首先，数据孤岛问题严重制约了医疗资源的优化配置。各医疗机构的信息系统相互独立，缺乏统一的数据标准和共享机制，患者在不同医院就诊时，病历数据无法互通共享，医生无法获取患者的完整就医历史。这不仅导致患者需要重复进行各类检查，增加了医疗费用负担，也造成了医疗资源的严重浪费，影响了诊疗效率和医疗服务质量。

其次，隐私安全问题日益突出。医疗数据涉及患者的个人隐私和敏感健康信息，传统中心化存储方式将数据集中存放在单一服务器，容易成为黑客攻击的目标，存在数据泄露风险。同时，患者对自己的医疗数据缺乏控制权，数据的访问和使用完全由医疗机构掌控，难以保障患者的知情权和隐私权。

第三，数据可信度难以保证。中心化系统中的数据修改权限集中，缺乏有效的防篡改机制和多方监督机制。医疗数据可能被恶意修改或删除，而这些操作往往难以追溯和举证。在医疗纠纷中，病历的真实性和完整性常常成为争议焦点，传统系统无法提供可靠的证据链和审计追溯能力。

第四，跨机构协作机制缺失。不同医疗机构之间缺乏统一的数据标准和信任机制，跨院诊疗和数据共享面临技术壁垒和信任障碍。各医院使用不同的信息系统，数据格式不统一，接口标准不一致，导致数据对接困难。即使部分地区建立了区域医疗信息平台，但由于缺乏有效的信任机制和激励机制，医疗机构对数据共享持谨慎态度，协作效果有限。

区块链技术作为一种新兴的分布式账本技术，具有去中心化、不可篡改、可追溯、多方共识等特性，为解决上述问题提供了创新性的技术方案。通过区块链的分布式存储，可以消除单点故障风险；通过密码学哈希链和共识机制，可以保证数据的完整性和不可篡改性；通过智能合约，可以实现自动化的访问控制和业务流程；通过多方参与的联盟链架构，可以建立医疗机构间的信任机制。

Hyperledger Fabric 作为 Linux 基金会主导的企业级区块链平台，特别适合医疗联盟链场景。它支持联盟链架构，允许多个医疗机构以平等身份参与网络；提供基于 MSP（成员服务提供者）的身份认证机制，确保只有授权用户才能访问数据；支持通道（Channel）机制，实现数据隔离和隐私保护；采用模块化设计，可根据实际需求灵活配置共识算法、加密方式等；具有较高的交易吞吐量和较低的延迟，能够满足医疗业务的性能要求。

本文设计并实现了一个基于 Hyperledger Fabric 区块链技术的社区医疗档案管理系统。该系统采用联盟链架构，构建了包含四个组织（协和医院、301医院、温江社区医疗中心、监管中心）的医疗联盟链网络，实现了用户管理、电子病历管理、跨院授权访问、药品订单管理和保险报销等核心功能。后端采用 Go 语言和 Gin 框架开发，通过 Fabric SDK 与区块链网络交互；前端使用 Vue.js 和 Element UI 构建，提供友好的用户界面；数据存储采用 MySQL 数据库与区块链双重存储机制，关键数据上链保证安全性，查询数据缓存到数据库提高性能。

系统实现了五种用户角色（管理员、医生、病人、药店、保险机构）的权限管理，通过智能合约保证数据的一致性和安全性。系统部署了15个智能合约函数，支持用户注册登录、病历创建查询、跨院授权申请审批、补充诊疗记录、药品订单管理、保险报销等完整业务流程。测试结果表明，系统功能完善，性能稳定，能够满足实际医疗场景的需求，为区块链技术在社区医疗领域的应用提供了可行的解决方案。

**关键词**：区块链；社区医疗；档案管理；隐私保护；智能合约

## Abstract

This paper presents a community medical records management system based on Hyperledger Fabric blockchain technology. The system addresses critical challenges in traditional healthcare systems including data silos, privacy breaches, and data tampering through blockchain's decentralization, immutability, and traceability features. Using a consortium blockchain architecture with four organizations, the system implements user management, electronic medical records, cross-hospital authorization, drug orders, and insurance claims. The backend utilizes Go and Gin framework, while the frontend employs Vue.js and Element UI, with a dual storage mechanism combining MySQL and blockchain. Test results demonstrate that the system achieves complete functionality, stable performance, and meets practical healthcare requirements.

**Keywords**: Blockchain; Community Healthcare; Medical Records Management; Privacy Protection; Smart Contract

## 第一章 绪论

### 1.1 研究背景与意义

#### 1.1.1 研究背景

随着信息技术的快速发展和"健康中国2030"战略的深入推进，医疗信息化已成为现代医疗体系的重要组成部分。特别是在社区医疗服务领域，信息化建设对于提升基层医疗服务能力、实现分级诊疗具有重要意义。然而，传统的医疗信息系统在实际应用中面临着诸多挑战：

1. **数据孤岛问题严重**

各医疗机构的信息系统相互独立，形成了大量的"信息孤岛"。患者在不同医院就诊时，病历数据无法互通共享，医生无法获取患者的完整就医历史。这导致患者需要重复进行检查（如血常规、CT扫描等），不仅增加了医疗费用，也造成了医疗资源的严重浪费。据统计，我国每年因重复检查造成的医疗资源浪费超过千亿元。

以社区医疗为例，患者可能在社区医院进行初诊，转诊到三甲医院后，由于缺乏数据共享机制，三甲医院的医生无法查看患者在社区医院的诊疗记录，只能重新进行全套检查，严重影响了分级诊疗制度的落实。

2. **隐私安全问题突出**

医疗数据涉及患者的个人隐私和敏感健康信息，传统中心化存储方式存在严重的安全隐患。一方面，中心化服务器容易成为黑客攻击的目标，近年来医疗数据泄露事件频发；另一方面，患者对自己的医疗数据缺乏控制权，数据被医疗机构单方面掌控，存在被滥用的风险。

根据《2023年全球数据泄露报告》，医疗行业是数据泄露的重灾区，平均每次泄露涉及数万条患者记录。这些泄露的数据可能被用于保险欺诈、身份盗窃等违法活动，给患者带来严重损失。

3. **数据可信度难以保证**

在中心化系统中，数据的修改权限集中在系统管理员手中，缺乏有效的防篡改机制。医疗数据可能被恶意修改或删除，而这些操作往往难以追溯。例如，在医疗纠纷中，病历的真实性常常成为争议焦点，传统系统无法提供可靠的证据链。

此外，医疗数据的审计追溯能力不足，当发生医疗事故或数据异常时，难以快速定位问题源头，影响了医疗质量管理和责任认定。

4. **跨机构协作机制缺失**

不同医疗机构之间缺乏统一的数据标准和信任机制，跨院诊疗和数据共享面临诸多障碍。各医院使用不同的信息系统，数据格式不统一，接口标准不一致，导致数据对接困难。即使部分地区建立了区域医疗信息平台，但由于缺乏信任机制，医疗机构对数据共享持谨慎态度，担心数据被滥用或泄露。

在社区医疗与大医院的双向转诊过程中，这一问题尤为突出。社区医生无法及时获取患者在上级医院的诊疗信息，影响了后续的康复治疗和健康管理。

**区块链技术的应用契机**

区块链技术作为一种新兴的分布式账本技术，具有去中心化、不可篡改、可追溯、多方共识等特性，为解决上述问题提供了创新性的技术方案：

- **去中心化架构**：消除单点故障风险，数据由多方共同维护
- **不可篡改性**：通过密码学哈希链保证数据完整性，任何修改都会被记录
- **可追溯性**：每笔交易都有完整的历史记录，支持全流程审计
- **智能合约**：自动执行业务逻辑，减少人为干预，提高效率
- **隐私保护**：通过权限控制和加密技术保护敏感数据

Hyperledger Fabric 作为 Linux 基金会主导的企业级区块链平台，特别适合医疗联盟链场景。它支持联盟链架构，允许多个医疗机构以平等身份参与网络；提供基于 MSP（成员服务提供者）的身份认证机制，确保只有授权用户才能访问数据；支持通道（Channel）机制，实现数据隔离和隐私保护；采用模块化设计，可根据实际需求灵活配置共识算法、加密方式等。

本研究正是基于 Hyperledger Fabric 平台，针对社区医疗档案管理的实际需求，设计并实现了一个安全、可信、高效的医疗信息共享系统。

#### 1.1.2 研究意义

本系统的研究与实现具有重要的理论意义和实践价值：

1. **理论意义**

（1）**探索区块链在社区医疗领域的应用模式**

本研究将区块链技术与社区医疗档案管理相结合，探索了联盟链在医疗数据共享场景中的应用模式。通过设计四组织联盟链架构（协和医院、301医院、温江社区医疗中心、监管中心），验证了区块链技术在多机构协作场景下的可行性和有效性。

系统实现了15个智能合约函数，涵盖用户管理、病历管理、授权管理、药品订单、保险报销、补充记录等全流程业务，为区块链在医疗领域的应用提供了完整的技术方案和实践参考。

（2）**研究联盟链架构下的多机构协作机制**

本研究设计了基于 Hyperledger Fabric 的联盟链协作机制，包括：
- 多组织共识机制：采用 OR 背书策略，任一组织成员即可背书交易，提高系统效率
- 跨院授权机制：通过智能合约实现患者对医疗数据的自主授权，医生申请-患者审批的双向确认流程
- 数据隔离机制：通过 Channel 和 MSP 实现组织间的数据隔离和访问控制
- 监管机制：监管中心作为独立组织参与联盟链，可查看所有交易记录，实现透明监管

（3）**提出基于智能合约的医疗数据访问控制方案**

本研究设计了细粒度的访问控制方案：
- 基于角色的权限控制（RBAC）：定义了管理员、医生、病人、药店、保险机构五种角色
- 基于授权的访问控制：跨院访问必须经患者明确授权，授权记录上链不可篡改
- 基于智能合约的自动化控制：访问权限验证由智能合约自动执行，避免人为干预
- 补充记录关联机制：医生可为病历添加补充诊疗记录（复诊、随访、急诊），形成完整的医疗历史链

2. **实践意义**

（1）**解决医疗数据孤岛问题，实现跨机构数据共享**

系统通过联盟链架构，将多家医疗机构连接在同一网络中，实现了医疗数据的互联互通。患者在任一医疗机构就诊产生的病历数据都会上链存储，经患者授权后，其他医疗机构的医生可以查询患者的完整就医历史，避免重复检查。

系统实现了"患者病历查询"功能，医生可以根据患者姓名或ID搜索病历，查看患者在不同医院的诊疗记录。这对于慢性病管理、疑难杂症诊断具有重要价值。

（2）**保障医疗数据安全，防止数据篡改和泄露**

系统采用多重安全机制保障数据安全：
- 密码加密存储：用户密码使用 bcrypt 算法加密，即使数据库泄露也无法破解
- 区块链不可篡改：病历数据存储在区块链上，通过哈希链和共识机制保证数据完整性
- 访问控制：基于 MSP 的身份认证，只有授权用户才能访问数据
- 审计追溯：所有操作都有交易ID记录，可追溯到具体的操作人和操作时间
- 双存储机制：关键数据存储在区块链（安全性），查询数据缓存在 MySQL（性能），兼顾安全和效率

（3）**提高医疗服务效率，减少重复检查和资源浪费**

通过数据共享，医生可以快速获取患者的历史诊疗信息，避免重复检查。系统实现了"完整病历历史查询"功能，可以查询患者的原始病历及所有补充记录，形成时间线视图，帮助医生全面了解患者病情发展。

系统还实现了药品订单管理和保险报销功能，患者可以在线提交报销申请，保险机构在线审核，简化了传统的线下流程，提高了办事效率。

（4）**为患者提供完整的医疗历史记录，支持精准医疗**

系统为患者提供了"健康档案"功能，患者可以查看自己的完整就医历史，包括：
- 基本信息：姓名、年龄、性别等
- 病历列表：所有就诊记录，按时间排序
- 就诊统计：就诊次数、就诊医院分布
- 用药记录：历史用药信息
- 数据可视化：通过图表展示健康趋势

这些完整的医疗数据为精准医疗、个性化治疗提供了数据基础，也方便患者进行自我健康管理。

（5）**支持分级诊疗和社区医疗发展**

系统特别关注社区医疗场景，通过区块链技术打通社区医院与大医院之间的数据壁垒。社区医生可以查看患者在上级医院的诊疗记录（需授权），为患者提供更好的康复指导和健康管理服务。同时，大医院的医生也可以了解患者在社区的随访情况，实现双向转诊的信息闭环。

系统实现了"补充诊疗记录"功能，支持医生为已有病历添加复诊、随访、急诊等补充记录，这对于慢性病管理和长期健康跟踪尤为重要。

（6）**推动医疗行业数字化转型**

本系统的实施为医疗行业的数字化转型提供了实践案例。通过容器化部署（Docker）、前后端分离架构、RESTful API 设计等现代软件工程实践，系统具有良好的可扩展性和可维护性。系统已成功部署到云服务器（http://www.lyt9999.cloud），支持多用户并发访问，验证了方案的可行性。

系统采用的双存储机制（区块链+MySQL）为医疗数据管理提供了新思路：关键数据上链保证安全性和不可篡改性，查询数据缓存到数据库提高查询性能，在安全性和性能之间取得了良好平衡。

4. 性能和可扩展性有待提高

# 第二章 相关技术介绍

## 2.1 区块链技术

### 2.1.1 区块链基本概念

区块链（Blockchain）是一种分布式账本技术，通过密码学方法将数据区块按时间顺序链接形成链式结构，具有去中心化、不可篡改、可追溯等特性。

**核心特征**：
1. **去中心化**：无需中心化机构，节点间点对点交互
2. **不可篡改**：通过哈希链和共识机制保证数据完整性
3. **可追溯**：每笔交易都有完整的历史记录
4. **透明性**：所有节点共享账本数据
5. **安全性**：采用非对称加密保护数据

### 2.1.2 区块链分类

1. **公有链**（Public Blockchain）
   - 完全开放，任何人可参与
   - 代表：比特币、以太坊
   - 特点：高度去中心化，性能较低

2. **联盟链**（Consortium Blockchain）
   - 部分开放，由联盟成员共同维护
   - 代表：Hyperledger Fabric、FISCO BCOS
   - 特点：性能高，适合企业应用

3. **私有链**（Private Blockchain）
   - 完全封闭，由单一组织控制
   - 特点：高性能，中心化程度高

**本系统采用联盟链架构**，适合医疗机构间的数据共享场景。

### 2.1.3 共识机制

共识机制是区块链网络中节点达成一致的算法：

1. **工作量证明（PoW）**：通过计算难题获得记账权
2. **权益证明（PoS）**：根据持有代币数量分配记账权
3. **实用拜占庭容错（PBFT）**：适合联盟链，性能高
4. **Raft**：Hyperledger Fabric 使用的共识算法

## 2.2 Hyperledger Fabric

### 2.2.1 Fabric 架构

Hyperledger Fabric 是 Linux 基金会主导的企业级区块链平台，采用模块化架构：

**核心组件**：
1. **Peer 节点**：维护账本和执行智能合约
   - Endorsing Peer：背书节点，执行交易并签名
   - Committing Peer：提交节点，验证并提交交易

2. **Orderer 节点**：排序服务，对交易排序并打包成区块

3. **CA 节点**：证书颁发机构，管理身份认证

4. **Channel**：私有通道，实现数据隔离

5. **Chaincode**：智能合约，实现业务逻辑

### 2.2.2 交易流程

Fabric 的交易执行采用"执行-排序-验证"模式：

1. **提案阶段**：客户端向背书节点发送交易提案
2. **背书阶段**：背书节点执行链码并返回签名结果
3. **排序阶段**：Orderer 对交易排序并打包成区块
4. **验证阶段**：所有节点验证交易并更新账本

### 2.2.3 Fabric 优势

1. **权限管理**：基于 MSP 的身份认证和访问控制
2. **隐私保护**：通过 Channel 实现数据隔离
3. **高性能**：支持并发执行，TPS 可达数千
4. **可扩展**：模块化设计，易于定制
5. **企业级**：成熟稳定，有大量生产案例

## 2.3 智能合约

### 2.3.1 智能合约概念

智能合约是运行在区块链上的程序代码，自动执行预定义的业务逻辑。

**特点**：
- 自动执行：满足条件自动触发
- 不可篡改：部署后无法修改
- 透明可信：代码公开，执行结果可验证

### 2.3.2 Fabric Chaincode

Fabric 的智能合约称为 Chaincode，支持 Go、Java、Node.js 等语言。

**生命周期**：
1. 打包（Package）
2. 安装（Install）
3. 批准（Approve）
4. 提交（Commit）
5. 调用（Invoke）

## 2.4 后端技术

### 2.4.1 Go 语言

Go 是 Google 开发的编程语言，具有以下特点：
- 高性能：编译型语言，接近 C 语言性能

- 参数绑定：自动解析请求参数

### 2.4.3 MySQL 数据库

MySQL 是开源关系型数据库，本系统用于：
- 用户认证信息存储
- 业务数据缓存
- 查询性能优化

**双存储机制**：
- 关键数据存储在区块链（不可篡改）
- 查询数据缓存在 MySQL（提高性能）

## 2.5 前端技术

### 2.5.1 Vue.js 框架

Vue.js 是渐进式 JavaScript 框架：
- 响应式数据绑定

### 2.5.2 Element UI

Element UI 是基于 Vue 的 UI 组件库：
- 丰富的组件
- 统一的设计风格
- 响应式布局
- 国际化支持

### 2.5.3 ECharts

ECharts 是数据可视化库，用于：
- 统计图表展示
- 数据分析可视化
- 实时数据监控

## 2.6 Docker 容器化

Docker 是容器化平台，用于：
- 区块链网络部署
- 环境隔离
- 快速部署
- 资源管理

**优势**：
- 轻量级：比虚拟机更高效
- 可移植：一次构建，到处运行
- 版本控制：镜像版本管理
- 快速启动：秒级启动

## 本章小结

本章介绍了系统开发涉及的关键技术，包括区块链基础、Hyperledger Fabric 架构、智能合约、后端技术栈（Go + Gin + MySQL）、前端技术栈（Vue.js + Element UI）以及 Docker 容器化技术。这些技术的结合为构建安全、高效的医疗信息管理系统提供了坚实的技术基础。

### 3.1.1 业务背景

传统医疗信息系统存在以下问题：

4. 跨机构数据共享缺乏信任机制

本系统旨在构建基于区块链的医疗信息共享平台，实现：
1. 多医疗机构间的安全数据共享
2. 医疗数据的防篡改和可追溯
3. 患者对医疗数据的自主控制
4. 跨院诊疗的授权访问机制

```go
func Register(c *gin.Context) {
    appG := app.Gin{C: c}
    body := new(model.RegisterBody)

    // 解析请求参数
    if err := c.ShouldBind(body); err != nil {
        appG.Response(http.StatusBadRequest, "失败", 
            fmt.Sprintf("参数解析错误: %s", err.Error()))
        return
    }

    // 参数验证
    if body.AccountName == "" || body.Username == "" || 
       body.Password == "" || body.Role == "" {
        appG.Response(http.StatusBadRequest, "失败", 
            "参数存在空值，请填写完整信息")
        return
    }

    // 检查用户名是否已存在
    existingUser, _ := db.GetUserByUsername(body.Username)
    if existingUser != nil {
        appG.Response(http.StatusBadRequest, "失败", 
            "用户名已存在，请更换用户名")
        return
    }

    // 密码加密
    hashedPassword := db.HashPassword(body.Password)

    // 调用智能合约注册到区块链
    var bodyBytes [][]byte
    bodyBytes = append(bodyBytes, []byte(body.AccountName))
    bodyBytes = append(bodyBytes, []byte(body.Username))
    bodyBytes = append(bodyBytes, []byte(hashedPassword))
    bodyBytes = append(bodyBytes, []byte(body.Role))
    
    // 根据角色传递不同参数
    if body.Role == "病人" || body.Role == "药店" {
        // 病人/药店：6个参数
        bodyBytes = append(bodyBytes, []byte(fmt.Sprintf("%d", body.Age)))
        bodyBytes = append(bodyBytes, []byte(body.Gender))
    } else {
        // 医生/管理员：10个参数
        bodyBytes = append(bodyBytes, []byte(body.Organization))
        bodyBytes = append(bodyBytes, []byte(body.OrganizationName))
        bodyBytes = append(bodyBytes, []byte(body.Department))
        bodyBytes = append(bodyBytes, []byte(body.DoctorTitle))
        bodyBytes = append(bodyBytes, []byte(fmt.Sprintf("%d", body.Age)))
        bodyBytes = append(bodyBytes, []byte(body.Gender))
    }
    
    // 执行区块链交易
    resp, err := bc.ChannelExecute("register", bodyBytes)
    if err != nil {
        appG.Response(http.StatusInternalServerError, "失败", 
            fmt.Sprintf("区块链注册失败: %v", err))
        return
    }

    // 解析区块链响应
    var data map[string]interface{}
    if err = json.Unmarshal(bytes.NewBuffer(resp.Payload).Bytes(), &data); err != nil {
        appG.Response(http.StatusInternalServerError, "失败", 
            fmt.Sprintf("解析区块链响应失败: %v", err))
        return
    }

    // 同步到数据库
    err = db.RegisterUser(body.Username, body.Password, body.AccountName, 
        body.Role, body.Organization, body.OrganizationName, 
        body.Department, body.DoctorTitle)
    if err != nil {
        fmt.Printf("警告: 数据库同步失败: %v\n", err)
    }

    appG.Response(http.StatusOK, "成功", data)
}
```

**实现要点**：
1. 参数验证：检查必填字段
2. 用户名唯一性检查
3. 密码加密存储（bcrypt）
4. 根据角色传递不同参数（6个或10个）
5. 区块链交易执行
6. 数据库同步

    department := ""
    doctorTitle := ""
    ageStr := ""
    gender := ""
    
    // 根据参数数量解析
    if len(args) == 6 {
        // 病人/药店注册：6个参数
        ageStr = args[4]         // 年龄
        gender = args[5]         // 性别
    } else if len(args) == 10 {
        // 医生/管理员注册：10个参数
        organization = args[4]      // 组织MSPID
        organizationName = args[5]  // 组织名称

        doctorTitle = args[7]       // 医生职称
        ageStr = args[8]            // 年龄
        gender = args[9]            // 性别
    }

    // 参数验证
    if accountName == "" || username == "" || password == "" || role == "" {
        return shim.Error("参数存在空值")
    }

    // 检查用户名是否已存在
    results, err := utils.GetStateByPartialCompositeKeys(stub, model.AccountV2Key, []string{})
    if err != nil {
        return shim.Error(fmt.Sprintf("查询账户列表失败: %s", err))
    }
    for _, v := range results {
        if v != nil {
            var account model.AccountV2
            err := json.Unmarshal(v, &account)
            if err != nil {
                return shim.Error(fmt.Sprintf("反序列化出错: %s", err))
            }
            if account.Username == username {
                return shim.Error("用户名已存在")
            }
        }
    }

    // 解析年龄
    age := 0
    if ageStr != "" {
        fmt.Sscanf(ageStr, "%d", &age)
    }

    // 创建账户对象
    newAccount := &model.AccountV2{
        AccountId:        stub.GetTxID()[:12],  // 生成区块链ID
        AccountName:      accountName,
        Username:         username,
        Password:         password,
        Role:             role,
        Organization:     organization,
        OrganizationName: organizationName,
        Department:       department,
        DoctorTitle:      doctorTitle,
        Age:              age,
        Gender:           gender,
    }
    
    // 写入账本
    if err := utils.WriteLedger(newAccount, stub, model.AccountV2Key, 
        []string{newAccount.AccountId}); err != nil {
        return shim.Error(fmt.Sprintf("%s", err))
    }
    
    // 返回成功结果
    accountByte, err := json.Marshal(newAccount)
    if err != nil {
        return shim.Error(fmt.Sprintf("序列化成功创建的信息出错: %s", err))
    }
    return shim.Success(accountByte)
}

### 5.5.1 密码加密

使用 bcrypt 算法加密密码：

```go
import "golang.org/x/crypto/bcrypt"

// 密码加密
func HashPassword(password string) string {
    bytes, _ := bcrypt.GenerateFromPassword([]byte(password), 14)
    return string(bytes)
}

// 密码验证
func CheckPasswordHash(password, hash string) bool {
    err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
    return err == nil
}
```

### 5.5.2 权限控制

基于角色的路由守卫：

```javascript
router.beforeEach((to, from, next) => {
  const userInfo = store.getters.userInfo
  const role = userInfo ? userInfo.role : null

  // 未登录跳转登录页
  if (!userInfo && to.path !== '/login') {
    next('/login')
    return
  }

  // 检查路由权限
  if (to.meta.roles && !to.meta.roles.includes(role)) {
    next('/403')
    return
  }

  next()
})
```

### 5.5.3 HTTP 请求封装

```javascript
import axios from 'axios'

const service = axios.create({
  baseURL: '/api/v2',
  timeout: 10000
})

// 请求拦截器
service.interceptors.request.use(
  config => {
    // 添加 token
    const token = localStorage.getItem('token')
    if (token) {
      config.headers['Authorization'] = `Bearer ${token}`
    }
    return config
  },
  error => {
    return Promise.reject(error)
  }
)

// 响应拦截器
service.interceptors.response.use(
  response => {
    const res = response.data
    if (res.code !== 200) {
      Message.error(res.msg || '请求失败')
      return Promise.reject(new Error(res.msg || '请求失败'))
    }
    return res
  },
  error => {
    Message.error(error.message)
    return Promise.reject(error)
  }
)

export default service
```

5. **前端应用开发**
   - 使用 Vue.js + Element UI 构建用户界面
   - 实现了7大功能模块的页面

   - 实现了基于角色的路由控制

6. **系统测试与部署**
   - 完成了功能测试、性能测试、安全测试
   - 系统通过率 100%，性能满足需求
   - 成功部署到生产服务器
   - 系统稳定运行，用户反馈良好

### 7.1.2 创新点

1. **双存储机制**
   - 关键数据存储在区块链（不可篡改）
   - 查询数据缓存在 MySQL（提高性能）
   - 兼顾了安全性和性能

2. **灵活的参数支持**
   - 智能合约支持6个或10个参数
   - 根据用户角色传递不同参数
   - 提高了系统的灵活性

3. **跨院授权机制**
   - 患者对医疗数据有完全控制权
   - 医生跨院访问需患者授权
   - 授权记录上链，可追溯

4. **完整医疗历史链**
   - 支持补充诊疗记录（复诊、随访、急诊）
   - 关联原始病历，形成完整历史
   - 补充记录不可修改，保证真实性

5. **数据可视化**
   - 用户统计图表
   - 联盟链架构可视化
   - 健康档案数据可视化
   - 提高了系统的易用性

### 7.1.3 技术难点与解决方案

1. **区块链与数据库同步**
   - 难点：区块链交易成功后，数据库同步失败
   - 解决：先执行区块链交易，再同步数据库，数据库失败不影响区块链

2. **跨院访问控制**
   - 难点：如何实现细粒度的访问控制
   - 解决：通过智能合约管理授权记录，前端根据授权状态控制访问

3. **参数灵活性**
   - 难点：不同角色需要不同参数
   - 解决：智能合约支持多种参数组合，后端根据角色传递不同参数

4. **性能优化**
   - 难点：区块链查询性能较低
   - 解决：使用 MySQL 缓存查询数据，区块链只存储关键数据

5. **前端权限控制**
   - 难点：不同角色看到不同页面
   - 解决：基于角色的路由守卫，动态生成菜单
