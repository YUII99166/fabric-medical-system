# 医疗信息管理系统数据库设计详细说明

## 1. 数据库架构概述

本系统采用**区块链+关系型数据库双存储架构**：

- **MySQL数据库**：用于用户认证、数据索引、快速查询和缓存
- **Hyperledger Fabric区块链**：存储核心业务数据，保证数据不可篡改和可追溯

### 1.1 架构优势

| 存储方式 | 用途 | 优势 |
|---------|------|------|
| MySQL | 用户认证、索引、缓存 | 查询速度快、支持复杂查询 |
| 区块链 | 病历、授权、订单等核心数据 | 不可篡改、可追溯、跨组织共享 |

### 1.2 数据流转

```
写入流程：应用层 → 区块链 → MySQL缓存
查询流程：应用层 → MySQL缓存 → (必要时)区块链验证
```

### 2.1 用户表（users）

**表说明**：存储系统所有用户的认证信息和基本资料，支持患者、医生、药店、管理员等多种角色。

**表结构**：

| 字段名 | 数据类型 | 长度 | 约束 | 默认值 | 说明 |
|--------|---------|------|------|--------|------|
| id | INT | - | PRIMARY KEY, AUTO_INCREMENT | - | 用户ID |
| username | VARCHAR | 255 | UNIQUE, NOT NULL | - | 用户名（登录账号） |
| password | VARCHAR | 255 | NOT NULL | - | 密码（SHA256哈希） |
| account_name | VARCHAR | 255 | NOT NULL | - | 账号名称（显示名） |
| role | VARCHAR | 50 | NOT NULL | - | 角色类型 |
| organization | VARCHAR | 255 | NULL | - | 组织MSPID |
| organization_name | VARCHAR | 255 | NULL | - | 组织名称 |
| department | VARCHAR | 255 | NULL | - | 科室（医生专用） |
| doctor_title | VARCHAR | 100 | NULL | - | 医生职称 |
| age | INT | - | NULL | - | 年龄（患者专用） |
| gender | VARCHAR | 10 | NULL | - | 性别（患者专用） |
| created_at | TIMESTAMP | - | NOT NULL | CURRENT_TIMESTAMP | 创建时间 |
| updated_at | TIMESTAMP | - | NOT NULL | CURRENT_TIMESTAMP ON UPDATE | 更新时间 |

**索引设计**：
```sql
PRIMARY KEY (id)
UNIQUE KEY uk_username (username)
INDEX idx_role (role)
INDEX idx_organization (organization)
INDEX idx_created_at (created_at)
```

**角色枚举值**：
- `patient` - 患者

- `insurance` - 保险机构

## 4. 数据同步机制

### 4.1 同步策略

**写入流程**：
1. 应用层接收请求
2. 数据写入区块链（调用智能合约）
3. 区块链返回交易ID和区块号
4. 数据同步到MySQL缓存表
5. 返回成功响应

**查询流程**：
1. 应用层接收查询请求
2. 优先从MySQL缓存查询
3. 如需验证，从区块链查询原始数据
4. 对比数据一致性
5. 返回查询结果

### 4.2 定时同步任务

**全量同步**（每天凌晨2点执行）：
- 从区块链读取所有数据
- 与MySQL缓存对比
- 修复不一致的数据
- 生成同步报告

**增量同步**（每小时执行）：
- 监听区块链事件
- 获取新增/更新的数据
- 同步到MySQL缓存
- 更新同步时间戳

### 4.3 数据一致性保证

**事务处理**：
```
BEGIN TRANSACTION
  1. 写入区块链
  2. 获取交易ID
  3. 写入MySQL
  4. 验证一致性
COMMIT / ROLLBACK
```

**冲突解决**：
- 以区块链数据为准
- MySQL仅作为缓存
- 定期校验和修复

## 5. 数据库优化策略

### 5.1 索引优化

- 为高频查询字段建立索引
- 使用复合索引优化多条件查询
- 定期分析索引使用情况

### 5.2 查询优化

- 使用缓存减少数据库访问
- 避免全表扫描
- 使用EXPLAIN分析查询计划

### 5.3 分区策略

对于大表（如日志表）采用分区：
```sql
-- 按月分区
```

## 8. 总结

本系统数据库设计采用双存储架构，充分发挥了MySQL和区块链各自的优势：

- **MySQL**：提供快速查询、复杂检索、用户认证等功能
- **区块链**：保证核心数据不可篡改、可追溯、跨组织共享

通过合理的表结构设计、索引优化和同步机制，系统能够在保证数据安全性的同时，提供良好的查询性能和用户体验。
