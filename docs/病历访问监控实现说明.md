# 病历访问监控实现说明

## 监控方法

### 1. 前端自动触发
在病历详情页面（`prescription/detail/index.vue`）的 `loadMedicalHistory` 方法中，成功加载病历后自动调用访问记录API。

**触发位置**：
- 文件：`fabric-mims-main/application/web/src/views/prescription/detail/index.vue`
- 方法：`loadMedicalHistory()` 
- 时机：病历数据加载成功后（response.code === 200）

**触发条件**：
```javascript
if (this.currentUser.account_id !== prescription.patient_id) {
  // 只有当访问者不是患者本人时才记录
  recordPrescriptionAccess({...})
}
```

### 2. 后端API处理
**接口**：`POST /api/v2/recordPrescriptionAccess`

**处理流程**：
1. 接收前端发送的访问信息
2. 检查是否为患者本人（本人访问不记录）
3. 生成唯一日志ID（UUID）
4. **先写入区块链**（确保数据不可篡改）
   - 调用智能合约 `recordPrescriptionAccess`
   - 带重试机制（最多3次）
   - 获取区块链交易ID（txID）
5. **再写入MySQL**（用于快速查询）
   - 记录IP地址和User-Agent
   - 保存区块链交易ID
6. 返回成功响应

**文件位置**：
- API层：`fabric-mims-main/application/server/api/v2/access_trace.go`
- 数据库层：`fabric-mims-main/application/server/db/access_log.go`

### 3. 区块链智能合约
**合约函数**：`recordPrescriptionAccess`

**参数**：
- logID：日志唯一ID
- prescriptionID：病历ID
- prescriptionNo：病历编号
- patientID：患者ID
- patientName：患者姓名
- accessorID：访问者ID
- accessorName：访问者姓名
- accessorRole：访问者角色
- accessorOrg：访问者组织MSPID
- accessorOrgName：访问者组织名称
- accessType：访问类型
- accessReason：访问原因

**文件位置**：
- 智能合约API：`fabric-mims-main/chaincode/api/access_trace.go`
- 数据模型：`fabric-mims-main/chaincode/model/model.go`
- 主合约：`fabric-mims-main/chaincode/chaincode.go`

**特点**：
- 数据写入区块链后不可篡改
- 每次写入都会生成唯一的交易ID（txID）
- 交易ID可用于追溯和验证

### 4. 双存储机制
**区块链存储**：
- 目的：确保数据不可篡改，提供法律效力
- 特点：永久保存、可追溯、可验证
- 查询：通过智能合约查询（较慢）

**MySQL存储**：
- 目的：快速查询和统计分析
- 特点：查询速度快、支持复杂查询
- 关联：保存区块链交易ID（txID）用于验证

### 5. 数据存储
**表名**：`prescription_access_logs`

**关键字段**：
- `log_id`：日志唯一ID
- `prescription_id`：病历ID
- `patient_id`：患者ID
- `accessor_id`：访问者ID
- `accessor_name`：访问者姓名
- `accessor_role`：访问者角色
- `access_type`：访问类型（view/edit/download）
- `accessed_at`：访问时间
- `ip_address`：访问IP
- `user_agent`：浏览器信息

## 常见问题排查

### 问题1：没有访问记录
**可能原因**：
1. 访问者是患者本人（本人访问不记录）
2. 表未创建成功
3. API调用失败
4. 前端代码未执行

**排查步骤**：
1. 打开浏览器控制台，查看是否有日志输出
2. 检查 `shouldRecord` 是否为 `true`
3. 查看Network标签，确认API是否被调用
4. 检查服务器日志是否有错误信息
5. 验证数据库表是否存在

### 问题2：表不存在错误
**解决方法**：
重启服务器，`db.go` 中的 `initTables()` 会自动创建表。

或手动执行SQL：
```sql
USE fabric_mims;
CREATE TABLE IF NOT EXISTS prescription_access_logs (...);
```

### 问题3：API返回500错误
**可能原因**：
- 数据库连接失败
- 字段值为空
- 表结构不匹配

**排查**：
查看服务器终端的详细错误信息。

## 性能考虑

1. **异步记录**：访问记录采用异步方式，不阻塞主流程
2. **静默失败**：记录失败不影响用户查看病历
3. **索引优化**：在patient_id、prescription_id等字段建立索引
4. **分页查询**：前端采用分页方式加载访问记录

## 隐私保护

1. **患者本人访问不记录**：避免产生大量无意义数据
2. **敏感信息脱敏**：IP地址仅记录用于安全审计
3. **访问权限控制**：只有患者本人能查看自己的访问记录
4. **数据不可删除**：访问记录一旦产生不可删除（区块链特性）

## 数据一致性保证

### 写入顺序
1. **先写区块链**：确保数据不可篡改
2. **后写MySQL**：用于快速查询

### 失败处理
- **区块链写入失败**：
  - 自动重试3次
  - 仍失败则继续写入MySQL（txID为空）
  - 记录警告日志
  
- **MySQL写入失败**：
  - 返回错误给前端
  - 区块链数据已保存（不可回滚）
  - 可通过区块链查询恢复数据

### 数据验证
通过txID关联区块链和MySQL数据：
```sql
-- 查询有txID的记录（已写入区块链）
SELECT * FROM prescription_access_logs WHERE tx_id IS NOT NULL AND tx_id != '';

-- 查询没有txID的记录（区块链写入失败）
SELECT * FROM prescription_access_logs WHERE tx_id IS NULL OR tx_id = '';
```
