# 区块链数据存储格式说明

## 访问日志在区块链中的存储方式

### 1. 数据结构（Go结构体）

在链码中定义的结构体：

```go
// PrescriptionAccessLog 病历访问日志（隐私溯源）
type PrescriptionAccessLog struct {
    LogID                    string `json:"log_id"`                     // 日志ID
    PrescriptionID           string `json:"prescription_id"`            // 病历ID
    PrescriptionNo           string `json:"prescription_no"`            // 病历编号
    PatientID                string `json:"patient_id"`                 // 患者ID
    PatientName              string `json:"patient_name"`               // 患者姓名
    AccessorID               string `json:"accessor_id"`                // 访问者ID
    AccessorName             string `json:"accessor_name"`              // 访问者姓名
    AccessorRole             string `json:"accessor_role"`              // 访问者角色
    AccessorOrganization     string `json:"accessor_organization"`      // 访问者组织MSPID
    AccessorOrganizationName string `json:"accessor_organization_name"` // 访问者组织名称
    AccessType               string `json:"access_type"`                // 访问类型：view/edit/download
    AccessReason             string `json:"access_reason"`              // 访问原因
    AccessedAt               string `json:"accessed_at"`                // 访问时间
}
```

### 3. 存储到区块链

#### 3.1 创建复合主键

```go
// 创建复合主键
key, err := stub.CreateCompositeKey(model.AccessLogKey, []string{logID})
// 结果：access-log-key\x007556dec5-c99f-4ddb-88c4-a8dba40ccbfb\x00
```

**复合主键格式：**
- 前缀：`access-log-key`
- 分隔符：`\x00`（NULL字符）
- 属性：`logID`
- 结束符：`\x00`

#### 3.2 写入账本

```go
// 写入账本（Key-Value存储）
if err := stub.PutState(key, accessLogBytes); err != nil {
    return shim.Error(fmt.Sprintf("写入账本失败: %s", err))
}
```

### 5. 为什么使用JSON而不是二进制结构体？

#### JSON格式的优点：

1. **人类可读**
   - 便于调试和审计
   - 可以直接查看数据内容
   - 便于问题排查

2. **跨语言兼容**
   - Go链码可以写入
   - JavaScript应用可以读取
   - Python工具可以分析
   - 任何支持JSON的语言都能处理

3. **灵活性**
   - 可以添加新字段而不破坏兼容性
   - 支持嵌套结构
   - 易于扩展

4. **富查询支持**（如果使用CouchDB）
   - 可以按任意字段查询
   - 支持复杂的查询条件
   - 支持索引优化

#### JSON格式的缺点：

1. **存储空间**
   - 比二进制格式占用更多空间
   - 字段名会重复存储

2. **性能开销**
   - 序列化/反序列化需要时间
   - 比直接内存操作慢

#### 替代方案对比：

| 格式 | 大小 | 速度 | 可读性 | 跨语言 | 富查询 |
|------|------|------|--------|--------|--------|
| JSON | 大 | 中 | ✓ | ✓ | ✓ |
| Protocol Buffers | 小 | 快 | ✗ | ✓ | ✗ |
| MessagePack | 中 | 快 | ✗ | ✓ | ✗ |
| 原始二进制 | 最小 | 最快 | ✗ | ✗ | ✗ |

### 6. 数据不可篡改性保证

#### 6.1 哈希链

每个区块包含前一个区块的哈希值，形成链式结构：

```
Block 1 → Block 2 → Block 3 → Block 4
  ↓         ↓         ↓         ↓
Hash1    Hash2     Hash3     Hash4
         (含Hash1) (含Hash2) (含Hash3)
```

如果修改Block 2的数据：
- Hash2会改变
- Block 3的"前一个区块哈希"不匹配
- 整条链失效

#### 6.2 默克尔树

区块内的交易通过默克尔树组织：

```
        Root Hash
       /         \
    Hash12      Hash34
    /    \      /    \
  Tx1   Tx2   Tx3   Tx4
```

任何交易的修改都会导致根哈希改变。

#### 6.3 数字签名

每个交易都有创建者的数字签名：
- 证明交易来源
- 防止交易被篡改
- 可以验证身份

#### 6.4 共识机制

多个节点验证并达成一致：
- 所有peer节点都有完整账本副本
- 修改需要通过共识
- 恶意节点无法单独篡改

### 8. 查询方式

#### 8.1 按主键查询（最快）

```go
key := stub.CreateCompositeKey("access-log-key", []string{logID})
value, err := stub.GetState(key)
```

#### 8.2 按范围查询

```go
// 查询所有访问日志
iterator, err := stub.GetStateByPartialCompositeKey("access-log-key", []string{})
```

#### 8.3 富查询（仅CouchDB）

```go
queryString := `{
  "selector": {
    "patient_id": "9f1a7a93bb90",
    "accessor_role": "doctor"
  }
}`
iterator, err := stub.GetQueryResult(queryString)
```

### 9. 总结

**存储格式：JSON字符串**
- 结构体 → JSON序列化 → 字节数组 → 区块链

**存储位置：**
- 区块链账本（不可变）
- 世界状态数据库（可快速查询）

**优势：**
- 人类可读
- 跨语言兼容
- 灵活扩展
- 不可篡改

**适用场景：**
- 医疗数据溯源
- 审计日志
- 访问记录
- 任何需要不可篡改证明的数据
